# Agentic Workflow / ハーネス 基礎ガイド

「エージェント」「ワークフロー」「ハーネス」という言葉の整理から、定番パターン、
よくある失敗までをまとめた入門ドキュメントです。Harness Studio のどの機能が
どの概念に対応するかも併記します。

関連: [HARNESS_DESIGN_GUIDE.md](HARNESS_DESIGN_GUIDE.md)(エクスポートの仕組み)/
[SELF_IMPROVEMENT_LOOP_GUIDE.md](SELF_IMPROVEMENT_LOOP_GUIDE.md)(自己改善ループ)

## 1. 用語の整理

| 用語         | 意味                                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| LLM 呼び出し | 1 回のプロンプト → 1 回の応答。最小単位                                                                                                   |
| エージェント | ツール(ファイル操作・コマンド実行・検索など)を使いながら、**モデル自身が次の行動を決めて**目標に向かうループ。Codex や Claude Code はこれ |
| ワークフロー | **人間があらかじめ決めた手順**に沿って LLM/エージェントを呼び出す流れ。「調査 → 計画 → 実装 → 検証」のような形                            |
| ハーネス     | 上のすべてを安定して動かすための足場一式。プロンプト、実行順、成果物の受け渡し、合否判定、ループ制御、停止条件                            |

重要な対比は **「ワークフロー(手順は人間が決める)」と「エージェント(手順はモデルが決める)」** です。

- ワークフロー: 予測しやすい・デバッグしやすい・品質が安定する。手順が分かっている仕事に向く
- エージェント: 柔軟だが暴走・迷走しうる。手順が事前に決められない探索的な仕事に向く

実務で強いのは組み合わせです。**外側はワークフローで統制し、各ステップの内側は
エージェントに任せる** — Harness Studio の Codex Runner はまさにこの構造で、
ステップの順番・ループ・合否判定はランナー(ワークフロー)が制御し、各ステップの
中身は Codex エージェントが自律的にやり遂げます。

## 2. 定番パターン

### 2.1 直列パイプライン(Prompt Chaining)

```
調査 → 計画 → 実行 → レビュー
```

タスクを工程に分割し、前工程の出力を次工程の入力にする。各工程のプロンプトが
小さく明確になるので、1 回の巨大プロンプトより品質が安定します。

→ Harness Studio: ステップを縦に並べるだけ。成果物の受け渡しは自動。

### 2.2 評価と修正のループ(Evaluator–Optimizer)

```
┌─ 実行(作る)→ チェック(判定する)─┐
└──── 不合格なら修正指示付きで再実行 ──┘
```

「作る役」と「判定する役」を分け、合格するまで反復する。**品質を作り込む最重要
パターン**です。判定役には「テストが通る」「チェックリストを満たす」のような
機械的に判定できる基準を与えます。

→ Harness Studio: 繰り返しブロック + 「チェック」ステップ。不合格理由と修正指示は
次の試行に自動で引き継がれます。

### 2.3 ルーティング(分岐)

入力の種類によって別の流れに振り分ける(例: バグ修正なら A、新機能なら B)。

→ Harness Studio: 現状は非対応(ループの出口以外の分岐はない)。代わりに
「計画」ステップで進め方を判断させるか、種類ごとにワークフローを分けてください。

### 2.4 並列化(Sectioning / Voting)

独立した作業を並走させる(ファイルごとのレビュー等)、または同じ問いを複数回
実行して多数決を取る。

→ Harness Studio: 現状は非対応(直列実行のみ)。必要なら書き出した Runner の
`run.mjs` を改造して `Promise.all` で並走させる拡張が可能です。

### 2.5 オーケストレーター + ワーカー

親エージェントがタスクを分解し、子エージェントに委任して結果を統合する。

→ Harness Studio: ワークフロー自体がオーケストレーター役を固定的に担う形です。
動的なタスク分解が必要なら、その部分を 1 つの「実行」ステップとして Codex に
委ねます(Codex はステップ内で自律的に動けます)。

## 3. 良いステップ・良いチェックの書き方

- **1 ステップ 1 責務**。「調査して実装してテストも書く」は分割する
- **指示は人に頼むつもりで**。何をするか + 何ができたら完了かを書く
- **チェックの基準は機械的に**。「良い感じ」ではなく「`npm test` が成功する」
  「チェックリスト 3 項目すべてに対応する記述がある」
- **ループには必ず出口**: チェックステップ or 終了条件 + 最大回数
- **共有コンテキストは再利用できる事実だけ**(規約・制約・前提)。タスク固有の
  内容は実行時のタスク文で渡す

## 4. よくある失敗モード

| 失敗             | 症状                                   | 対策                                                                       |
| ---------------- | -------------------------------------- | -------------------------------------------------------------------------- |
| 合格基準が曖昧   | ゲートが常に PASS(または常に FAIL)する | 機械判定できる基準に書き直す                                               |
| 出口のないループ | 同じ修正を繰り返して進まない           | 最大回数 + 終了条件。修正指示を引き継ぐ(Runner は自動)                     |
| コンテキスト肥大 | 後半のステップほど品質が落ちる         | ステップ出力を「次工程に必要な要約」にする(期待する出力で指定)             |
| 工程の混在       | 調査のつもりがコードを書き始める       | 種類プリセットの役割文 + 「〜しない」を指示に明記                          |
| ツール不足       | 「確認できません」で止まる             | 実行環境(Codex のサンドボックス・対象ディレクトリ)がその作業をできるか確認 |

## 5. どこから始めるか

1. テンプレート(コード変更 / 調査レポート / コードレビュー)を開く
2. 指示文を自分のプロジェクトの言葉に書き換える
3. 共有コンテキストに規約・制約を 3〜5 行書く
4. Codex Runner で小さいタスクを 1 回流し、`runs/` の成果物を読む
5. うまくいかなかったステップの指示を直す — これを繰り返す

この 5 番を AI 自身にやらせるのが「自己改善ループ」です。続きは
[SELF_IMPROVEMENT_LOOP_GUIDE.md](SELF_IMPROVEMENT_LOOP_GUIDE.md) へ。
