# ハーネス設計ガイド — 「設計」を「実際に動く形」にするために

このドキュメントは、Harness Studio が扱う「AI エージェント向けハーネス設計」とは何か、
それが現実にどう実装されるのか、そして Harness Studio のエクスポートがどうやって
「実際に使える形」を生成しているのかを説明します。

## 1. ハーネスとは何か

LLM エージェントの「ハーネス(harness)」とは、**モデルそのものの外側にあって、
エージェントを安定して目的に向かわせるための足場一式**のことです。モデルは賢くても、
裸のままでは「何をどの順でやるか」「いつ止まるか」「結果が良いか悪いか」を
管理できません。それを担うのがハーネスです。

ハーネスは具体的には次の部品でできています。

| 部品                                      | 役割                                                   | Harness Studio での対応概念  |
| ----------------------------------------- | ------------------------------------------------------ | ---------------------------- |
| システムプロンプト / リポジトリガイダンス | 全ステップ共通の前提知識・規約・リスク                 | **Context Pack**             |
| ステッププロンプト                        | 1 ステップ分の指示(目標・成功条件・出力形式・停止条件) | **Prompt Brief**             |
| ステップ契約                              | ステップの入力・成果物・許可される行動・品質ゲート     | **Step Contract**            |
| 成果物の受け渡し                          | 前ステップの出力を次ステップの入力に接続する仕組み     | **Handoff Contract(エッジ)** |
| ワークフロー制御                          | ステップの実行順序(誰が・いつ・何を)                   | **ノードとエッジ(実行計画)** |
| 品質ゲート                                | 「続行してよいか」を機械的に判定する関門               | **Gate ノード**              |
| ループ制御                                | 合格するまで作業↔検証を反復し、上限で打ち切る          | **Workflow Loop**            |
| ランタイム                                | 上記すべてを実際に動かす実行環境                       | **エクスポート先(下記)**     |

ポイント: **設計データ(md/json)はハーネスの「仕様書」であって、ハーネス本体ではありません。**
ハーネス本体とは「仕様書どおりにモデル呼び出し・成果物受け渡し・ゲート判定・ループを
実行する仕組み」です。これが従来の Harness Studio に欠けていた部分です。

## 2. ハーネスは現実にどう実装されているか

代表的な実装形態は 3 つあります。

1. **Claude Code などのエージェント CLI に載せる(ノーコード)**
   - `CLAUDE.md` がリポジトリガイダンス(= Context Pack)
   - `.claude/commands/*.md` のスラッシュコマンドがステッププロンプト(= Prompt Brief)
   - オーケストレーター用コマンドが実行順・ループ・ゲート処理を指示
   - ファイル操作・コマンド実行などのツールは Claude Code が提供
2. **API の上に自前の実行ループを書く(コード)**
   - 各ステップ = Anthropic Messages API への呼び出し
   - 成果物 = 呼び出し結果のテキストを保存し、次の呼び出しのプロンプトに注入
   - ゲート = 構造化出力(JSON Schema)で PASS/FAIL を機械可読に取得
   - ループ = ゲートの判定結果と最大反復回数で制御
3. **Managed Agents / Workflow 基盤に載せる(ホスティッド)**
   - エージェント定義・セッション・成果物管理をプラットフォーム側が担う

Harness Studio は 1 と 2 をエクスポートとして生成します。

## 3. 「実際に使える形」に必要だったもの

「md/json を出力するだけ」から「動く形」に進むために、次の 6 つを追加しています。

1. **実行計画(Execution Plan)** — キャンバスのノードとエッジをトポロジカルソートし、
   ループをひとかたまりの実行単位に畳んだ「実行順序」。`harness.json` に同梱されます。
2. **タスク注入点** — 設計は再利用可能なテンプレートなので、実行時に「今回のタスク」を
   差し込む場所(`$ARGUMENTS` / `{{TASK}}`)を全ステッププロンプトに用意。
3. **成果物の受け渡し機構** — 各ステップの出力をファイルとして保存し、後続ステップの
   プロンプトに「前ステップの成果物」として注入(`.harness/runs/` / `runs/<timestamp>/`)。
4. **ゲートの機械可読化** — Gate ノードは PASS/FAIL・理由・修正指示を構造化して返し、
   ワークフロー制御がそれを読んで分岐・反復する。
5. **ループ制御の実装** — 最大反復回数、終了条件判定、FAIL 時のフィードバック引き継ぎ、
   上限到達時の UNRESOLVED 報告。
6. **ランタイムと配布形態** — Claude Code(ツール付き)または同梱の実行エンジン
   (`run.mjs`)が上記を実際に動かす。ZIP でダウンロードしてそのまま使える。

## 4. 2 つのエクスポートの使い分け

### Claude Code Pack(推奨: コードを書き換えるワークフロー)

ZIP の中身をリポジトリのルートに展開すると、そのまま使えます。

```
CLAUDE.md                           ← Context Pack 由来のリポジトリガイダンス
.claude/commands/harness-run.md     ← /harness-run <タスク> で全ステップ実行
.claude/commands/harness-step-*.md  ← ステップ単体実行用コマンド
harness/workflow.md                 ← 実行計画と Mermaid 図
harness/harness.json                ← 設計の機械可読データ
```

Claude Code 自体がファイル編集・コマンド実行・検証のツールを持っているため、
**コードベースを実際に変更するハーネス**はこちらが本命です。

### Agent Runner Pack(推奨: テキスト成果物のパイプライン / アプリ組み込み)

```
run.mjs          ← 実行エンジン(@anthropic-ai/sdk 使用、claude-opus-4-8)
manifest.json    ← 実行計画(ステップ順・ループ・モデル設定)
system.md        ← 共通システムプロンプト(Context Pack 由来)
prompts/*.md     ← ステッププロンプト(編集可)
harness.json     ← 設計の原本
```

```bash
npm install
export ANTHROPIC_API_KEY=sk-ant-...
node run.mjs "実行したいタスク"
```

調査 → 設計 → 執筆 → レビュー → ゲートのような**テキスト成果物を作るワークフロー**を
完全自動で実行します。エンジンは 300 行弱の素直な JavaScript なので、自社アプリへの
組み込みやツール追加の出発点としても使えます。

## 5. 良いハーネスを設計するためのチェックリスト

- **各ステップの成果物が明文化されているか**(Step Contract の Produced Artifacts)。
  次のステップは前のステップの成果物しか見えない前提で書く。
- **ゲートの判定基準が機械的に判定できる文か**。「良い感じになっている」ではなく
  「npm run build が成功する」「受け入れ条件 3 件すべてに対応する記述がある」。
- **ループに必ず出口があるか**。終了条件 + 最大反復回数 + 上限到達時の挙動。
- **Context Pack に入れるのは再利用可能な事実だけか**。タスク固有の指示は
  Prompt Brief 側に置く(キャッシュと再利用性のため)。
- **停止条件(Stop Rules)があるか**。エージェントが暴走せず、判断が必要な場面で
  人間に返す境界を決める。

Validate タブの検証はこのチェックリストの多くを自動チェックします。
